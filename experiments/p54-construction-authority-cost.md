# P54 — Construction authority incremental cost

## Decision

**D — Invalid for event-scoped activation.** P53's Construction-owned request still passes the p720 purchase and postcondition. The P54 D/D-repeat activation diagnostic did not reach that same authority: the runtime latch reported event-fed mode, but the active Construction adapter reported it as disabled, then rejected the request as stale because the prior publication identity was unavailable. The P53 and P54 instrumentation is behind the experimental test-surface build flag. The ordinary production build retains no P53/P54 admission module, request polling, experimental price/control probes, or added root identity samples. This evidence does **not** pass the independent ≤2% renderer CPU requirement.

### Root-read reconciliation

P53's “six extra root observations” came from its exact runner adding two to a synthetic counter for each of three context samples. That code did not invoke `readRoot()`. P54 instruments the actual `GameRootStateSource.readRoot()` callsite in [`vue-capture.ts`](../src/adapters/evolve/vue-capture.ts), and samples that counter before the runner's own checkpoint snapshot read.

For C, the measured request-authority scopes contain 3 context root reads, 7 reservation-evidence root reads, and 2 native-control/price root reads: 12 actual reads within those scopes. This is not the net incremental difference from B because B already performs overlapping root reads for ordinary Construction work. Across the full replay, the actual root-call counter at p720 is 48,969 for B and 48,973 for C, a net observed difference of 4. The six-read P53 attribution is therefore unsupported; it should not be replaced with “12 extra.”

By API, dormant A and pending C p719 add zero request-specific native calls. Active C adds two read-only `buildQueue.setData` calls and performs one `city-rock_quarry.action`; B performs that same gameplay action once, so only the two price calls increase the B-to-C API sequence. The complete C execution still includes the single P41 reservation sample and its seven actual root reads.

The runner records cumulative synchronous cost, maximum operation cost, and maximum callback cost with browser `performance.now()`. Every recorded duration was 0 ms at the observed resolution. That means the durations are below the usable resolution; it does **not** mean the work costs zero. No conservative CPU estimate is supported. Retained heap allocation counts were not instrumented; the evidence reports retained request references, mutable-root retention (none), and serialized evidence bytes instead.

The D diagnostic reports runtime latch mode `true`, active adapter mode `false`, and zero local pending-request checks. The owner rejected it as `stale: construction-publication-identity-mismatch`; it made no Quarry action. D-repeat matched D's state, native control use, exports, and RNG. This is not evidence that a local pending check is free or measured: the intended local-check path never ran.

The P53 test-hook property lookup continues at every existing Construction boundary after purchase or cancellation, including when the request is absent. These are local test-only property reads; they do not schedule work or trigger native observation. The D event latch itself is event-fed and has no polling loop, but it did not reach the active owner and therefore cannot replace the P53 lookups in this result.

## Event-scoped activation and performance assessment

1. **No-request native observations:** no additional P53/P54 native observation occurred in A. The test-only request property was still read at the normal Construction boundary; the ordinary production bundle compiles the P53/P54 path out.
2. **Minimum local activation check:** the expected future check would be a single local pending-reference check at the existing Construction boundary. P54 did not measure it because D's active adapter did not select that path.
3. **Native observations during execution:** C needed the complete P41 reservation sample, three identity samples, and two fresh current-price checks. Both `buildQueue.setData` calls remain required. The native Quarry action and its debit/postcondition also remain authoritative.
4. **Two price probes:** yes, admission and execution must independently verify the current native price. P54 kept both.
5. **Invalidation:** the captured root-replacement callback can invalidate request state without a new native scan. A production event source still needs owner-scoped delivery.
6. **Feature disabled:** P50's compiled-output regression confirms zero P53/P54 admission bytes, diagnostic request polling, experimental price/control probes, and extra root/progression identity samples in ordinary production.
7. **Renderer CPU:** production admission remains blocked. P46 established that the current noisy paired comparison cannot resolve a 2% change. P54 does not rerun or reinterpret that protocol. A representative renderer-level method with enough precision to resolve ≤2% is still required.

No suitable existing production lifecycle delivers a player-selected Construction request. The test event sink is not player authorization, and D shows that it did not bind to the active Construction adapter or preserve the prior-publication identity. A concrete opt-in feature and an owner-scoped event source are needed before revisiting this architecture. No polling timer, global allocator listener, new DOM observation, retained root, settings UI, Jobs assignment, Gather action, or campaign extension was added.

`test-artifacts/benchmark/settings/baseline-tuned.json` remains absent. No benchmark claim uses it. P45's Food-stock calibration failure remains a separate Jobs safety blocker.
