## Method

`p3-vue-getter-attribution.mjs` extends the P2 CDP CPU sampler. It uses the exact Chromium runner, the existing late and mid saves and settings, seed 42, 600 warmup periods, and a 1,000-period sample window. Four profiles were collected (two per fixture) at 1 ms sampling. The Vue profiler itself runs outside the bundle; production source and the userscript were not instrumented. Reproduce with:

```text
node experiments/p3-vue-getter-attribution.mjs --scenario both --repeats 2 --warmup 600 --periods 1000 --sampling-us 1000
```

The analyzer recognizes Vue `get` frames and walks each sampled stack toward its initiating caller. It separates direct automation adapter reads, captured-control discovery, automation initiated game/native work, upstream game work, and other/unknown work. Automation initiated native game work is not counted as a removable opportunity. Function self samples are exclusive estimates; getter samples attributed to callers are inclusive stack observations. Sampled shares are estimates and overlap by nature; renderer CPU and CDP `TaskDuration` are totals, not replacements for attribution.

The sample repeats also showed two large getter stacks under the automation `wrapper` and `invokeControl` functions. They account for the automation initiated native-game category above: the call path reaches reactive game actions, rendering, and native price work. They are intentionally excluded from the removable-read estimate.

## Optimization decision and A/B

No optimization was selected. The largest directly attributed adapter paths (`readCapturedActionAvailability` and `readCapturedBuildingUnlockStateRecords`) together account for at most about 1.3% of all sampled work, below the required 2% renderer CPU acceptance threshold even under an unrealistic assumption that every attributed sample disappears. The capture loops also contain distinct action/record checks, and a cross-action cache would require freshness and fail-closed regressions without enough measured headroom to justify that risk.

The controlled unprofiled baseline/candidate A/B was not run because Phase B rejected the candidate pool before a production candidate existed. The four profiling runs are attribution evidence, not an A/B result. No production optimization, focused regression suite, or candidate CPU claim is present.

## Recommendation

Stop P3 without a production change. If future work targets a capture with a larger measured budget, first identify the narrow shared fields and prove that local reuse stays within one synchronous observation; retain native mutation invalidation and the existing fail-closed paths. The next evidence should be a production-only sample specifically around the price-authority snapshots if that path remains a concern.
