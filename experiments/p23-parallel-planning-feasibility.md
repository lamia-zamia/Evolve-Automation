# P23 — Web Worker feasibility for parallel Evolve planning

## Decision C — insufficient isolation and measurement

No worker prototype or production behavior was added. P22 does not measure any candidate's pure computation independently from its live native input capture, and its controlled Chromium runner replaces `window.Worker` with a timer-only `ControlledWorker`. A Blob-backed planning worker therefore cannot be tested in the benchmark runner's actual Worker context without changing the harness and invalidating the preserved P22 baseline. There is not enough evidence to select a planner, establish worker scheduling, or estimate total CPU cost.

The largest measured candidate-level planning boundary is Jobs, but it includes fresh native price capture. Selecting it from the 7.76 ms total would violate the required pure-computation comparison. Market and Construction totals likewise include native reads, DOM/control work, or execution. The pure-cost ranking is therefore **unmeasured**, not evidence that a particular planner is expensive.

## Worker environment and authority

- The runner is real Headless Chromium 151.0.7922.71, but `tools/chromium/bridge.js` deliberately assigns `window.Worker = ControlledWorker`. Its constructor records the URL and its `postMessage` only handles game timer `start`/`clear`; it does not execute worker source or deliver worker responses. This is the game's controlled timer simulation, not a real planning Worker.
- The repo's `scripts/worker-planning-spike.mjs` separately bundles an existing Research-goal candidate planner and exercises a Blob URL worker on the upstream Evolve page. That is a different experiment and candidate. It does not prove worker execution through this controlled runner, compatibility with a userscript manager's exact injection/CSP context, or compatibility with Jobs, Market, Construction or demand snapshots.
- The production build has no import/reference to `createPlanningScheduler`, `createEmbeddedPlanningWorker`, or the Research-candidate worker. Those modules are test/experiment code. Worker source is not distributed by the normal build; the spike bundles it separately with esbuild.
- The scheduler and spike use one worker, one active request and at most one latest pending request. They are not wired to production owner lifecycle. Thus root replacement, disable, reset, reload and shutdown cleanup for a planning worker in the production userscript are not established by this task.
- Current owners retain authority: Jobs captures then executes; Market checks captured route/control identity and verifies each mutation; Construction interleaves capture, planning and execution. A worker proposal would require owner-specific current-state validation before the existing executor. No proposal was admitted or executed here.

## Scheduling and performance limits

Each candidate currently plans in a synchronous owner call followed by same-cycle action or verification. Returning asynchronously in that same cycle would require deferring the owner and changing when later owners observe mutations. Carrying a proposal to the next cycle would plan against old prices/resources/controls and needs explicit fresh validation plus proof that every decision input is equivalent. P22 supplies neither. We did not block a cycle, pipe stale decisions forward, or execute worker output.

P22's three identical renderer CPU controls varied by 3.23%; TaskDuration controls varied by 3.91%. This exceeds the 2% sensitivity target. P22 recorded no worker CPU, transfer overhead, snapshot size, worker memory, or worker initialization cost for these candidates. No renderer CPU delta or total CPU claim can be made.

## Decision and follow-up boundary

Decision C applies because the pure planner cost and exact-runner Worker behavior needed to satisfy candidate selection and parity are not established. Under the task's stop rule, no worker prototype or workaround was added. Retrying requires a separately scoped exact-runner measurement path that preserves the production bundle and can run a real worker independently from the game's controlled timer worker, plus instrumentation that times only captured pure planner input and computation. Until then, a prototype would demonstrate infrastructure rather than a measured parallel workload.
