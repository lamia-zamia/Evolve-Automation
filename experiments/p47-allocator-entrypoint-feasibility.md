# P47 — Zero-new-capture allocator entry-point feasibility

## Decision: C — no defensible trigger

The retained evidence does not establish a natural, fresh owner publication that can qualify a selective coordinator call. A newly unlocked Quarry Worker row is the narrowest plausible condition: the normal Jobs capture already contains row availability, so consuming that prepared value would need no extra native catalog read. The retained Standard/Human run has no native Quarry purchase or Quarry Worker assignment, but it does not retain a cycle-by-cycle Jobs catalog. P43 begins with the row already unlocked after P42's test-only Construction intervention. P45 stores food-only points derived from P43 B; the separate late-game P46 artifact has no prepared Jobs publication history.

The Jobs input also lacks the work-cycle, root, progression, source-owner, and per-row control generation envelope requested for a synchronous diagnostic boundary. Construction saving intent cannot fill that gap: P40 shows that the completed intent at work cycle 89 was Farm while Construction was ordering Quarry in cycle 90. P37–P45 keep their diagnostic and fail-closed authority limits.

Stage 2 therefore did not establish a qualified trigger. Stages 3–5 were gated off: no coordinator contract, runtime interception, A/B/B-repeat parity run, or coordinator timing was added. The machine evidence uses `null` for unmeasured coordinator costs; it does not call them zero. Production source and behavior are unchanged.

## Stage 2 — Selective activation candidates

### Newly unlocked Quarry Worker row

This is the strongest candidate because the normal Jobs catalog already contains `unlocked` for each captured row. A synchronous local comparison against the immediately preceding publication could avoid another native scan, provided both values have compatible owner identities. The evidence does not establish a natural transition suitable for a P47 coordinator:

- P38 ran the Standard/Human replay through p10000. It recorded 2,500 ordinary Jobs executions in each A, B, and B-repeat arm. The captured p688 Jobs input had no live Quarry Worker row; the production report records no native Quarry purchase and no Quarry Worker assignment through its p10000 checkpoints. P38 did not retain a cycle-by-cycle Jobs catalog, so the transition count is **unrecorded**, not zero.
- P43 has 1,161 events per arm from p720 through p10000. Quarry Worker is already unlocked in the first event in both arms; there are zero row-entry or unlock transitions in the observed trace. This is post-P42 test Construction authority and does not show a natural unlock event.
- P43 is also not zero-new-capture evidence: its trace added 1,161 Food observations, 2,322 control-generation reads, and one Food breakdown read per Jobs cycle. Those costs belong to P43's diagnostic hook and are excluded from P47 runtime claims.
- P45 stores 1,229 food-stock points derived from P43 B and no Jobs, Construction, queue, Research, or generation fields. The separate P46 800-period late-game profile does not retain prepared Jobs publications. Late-game trigger frequency is therefore unavailable, not zero.

The row is an observable capability change, but a row alone does not establish an unsatisfied native production target, a complete worker commitment set, or permission to override native Jobs. Adding a previous-publication tracker and an identity envelope might be a future design; P47 does not count that as an existing qualified owner event.

### Other candidates rejected

- **Construction target change:** P40's p720 event shows current Construction work/order cycle 90 while the saving reservation came from completed publication 89 and named Farm; current Construction order was Quarry. Reading current order in place of completed intent would violate P40/P41 authority. P43's later target publications are test-intervention-linked.
- **Material shortage or resource demand change:** demand is memoized per epoch and derived from several owners. No existing event publishes a common, same-cycle demand transition. Sampling it on cache miss can also trigger Research/reservation work. A shortage is evidence to inspect, not player spending authority.
- **Native queue change:** queue entries are genuine player commitments, but the source is read lazily by reservation sampling and has no event tied to the Jobs work cycle. A second queue read is outside the zero-new-capture condition.
- **Jobs allocation request:** `onCoherentPlan` reports an ordinary decision after its native execution succeeds. It does not request another coordinator or grant authority to change other owners' work.
- **P37 economic objective:** its objective is marked `playerSelected: false` with `executionAuthority: none`; it cannot serve as an activation or spending authorization.

## Stages 3–5 — Gated off

No pure coordinator contract was implemented because Stage 2 did not establish a valid trigger and prepared identity envelope. No code returns `not-triggered`, `insufficient-evidence`, `blocked-by-authority`, or `candidate-observed`; those statuses remain a future contract requirement if a valid trigger is found.

No test-surface interception or A/B/B-repeat runtime proof was run. No coordinator evaluation, activation check, input preparation/copy, callback increment, or retained diagnostic memory was measured. The JSON uses null for these values. The P47 evidence tooling itself only reads retained files and is not a game callback.

The Chromium runner contracts passed. A P47 gameplay parity comparison was gated off with the trigger experiment. The existing missing `test-artifacts/benchmark/settings/baseline-tuned.json` native-parity fixture remains a coverage limitation already recorded by P46; no replacement fixture or parity evidence was fabricated.

P46's calibrated renderer CPU analysis still does not detect a calibrated 2% effect: its paired 2% confidence interval includes zero. No small callback-time value or P47 result is a renderer CPU result, and no ≤2% pass is claimed.

## Stage 6 — What the architecture supports

1. **Meaningful opportunity without a new native capture?** A prepared Jobs row can show that a productive role has become available. P47 did not find a naturally observed transition in the retained authenticated stream. The retained data is insufficient to establish that this is a meaningful allocation opportunity rather than a capability-only change.
2. **Selective invocation on owner publication change?** A local comparison of consecutive Jobs publications is technically possible, but there is no existing change event or publication identity envelope. Selective coordinator execution has not been established at the current boundary.
3. **Complete source authority at one synchronous boundary?** No. Jobs, Foundry, Construction intent, Research offers, demand, and queues have separate lifecycles. Their values cannot be joined by game period alone.
4. **Unavailable P37–P45 dependencies:** no player-selected economic objective; no native Quarry purchase or actual Quarry Worker row at the P38 boundary; no complete cross-owner worker commitment ledger; no same-cycle Construction commitment replacing its previous-cycle saving intent; no coeval queue/reservation identity; and no complete same-boundary authority input in the P43/P44 formula projections. P41's fail-closed correction remains in force.
5. **Observations unavoidable for a real allocation decision:** a selected objective or owner request, complete worker/servant/Craftsmen and competing-job commitments, current Construction reservation and target authority, queue reservations, current resource holdings and native costs, and fresh relevant controls/prices. Which are already prepared for a particular cycle must be established by a shared generation envelope; P47 did not recapture them.
6. **Can observation-only work be bounded separately?** In principle, a small pure predicate over one already-prepared, immutable, identity-complete input can be bounded independently of a production allocator. P47 did not implement or time one because the required trigger/input pair is not established.
7. **What production opt-in still requires:** a genuine trigger measured in both authentic Standard/Human and bounded late-game owner streams; identity and invalidation checks at the actual synchronous boundary; A/B/B-repeat gameplay, native-action, RNG, and export parity; separately measured activation, evaluation, preparation, copying, callback, maximum-cycle, and retained-memory costs; explicit execution authority; and a calibrated renderer CPU comparison that resolves the independent ≤2% gate.
