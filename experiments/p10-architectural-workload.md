## Decision

**B — Bounded scheduling is the proposed experiment.** The largest observed native observations are consumed by current decisions and cross-feature demand, and P5–P9 have already removed or rejected the safe local reductions they exposed. The measurements do not demonstrate a performance improvement from bounded scheduling. Do not cache, skip, or stagger those live observations. For autonomous allocation, separate a potentially large pure planner from immediate controls and test deterministic bounded slices over one immutable captured input. Execute no allocation command until the plan is complete and every input dependency is still valid. This is an architecture experiment proposal only; P10 adds no production optimization and does not start autonomous allocation or Research Gate B2.

P8 invalidated renderer CPU A/B as an acceptance method for this workload: even calibrated 10% injected work was not reliably detected. P10 therefore uses exact-runner operation counts and source-mapped sample weights only. Sample weights rank work; they are not renderer CPU savings estimates.

## Ordered worktick and dependency graph

`capturedRuntimeWorkTick` / `runCycle` in `src/bootstrap/captured-runtime-control.ts` is the application composition closure. The order below is the active late-fixture path; settings and availability gates omit some phases. Mid takes the same shared prefix and additionally performs three post-Research demand preparations.

```text
cycle start
  reset per-cycle state; invalidate prior demand; refresh discovered settings
  incomplete capture / master / Evolution gates
  demand prerequisites
  construction demand preparation (Building controls, current Building targets)
  [project demand discovery]
  [autoTrigger discovery and target capture]
  [autoFleet discovery]
  construction saving discovery (Construction options and candidate prices)
  [Gather claim sampling]
  pre-Gather demand (Research offer observation + shared demand sample)
  [Gather action]
  Market → Hell → Galaxy Market → Mining Droid → Graphene → Alchemy → Pylon
  Quarry → Mine → Extractor → Smelter → Storage → Replicator
  [Trigger; if active it suppresses Research and Build]
  Research
  [if progression changed: invalidate demand/offers and re-prepare Building demand]
  Build
  Factory
  Jobs + Craftsmen (combined), or separate Jobs / Craftsmen
  Fleet → Mech → Genetics → Minor Trait → Craft
  Mercenary → Spy → Espionage → Battle
  Tax → Government → Nanite → Supply → Eject
  [pre-Power Research / Project / Building demand observations]
  Power → Prestige
  Shapeshift → Psychic → Ocular Powers → Wish → Mutate Traits
cycle end
```

The native control sequence above is ordered. A later phase can deliberately consume a sample made earlier; it is not an independent copy of the same work. The specific demand and construction chain is:

```text
Construction demand preparation
  -> current Building catalog -> established storage/build targets
construction saving discovery
  -> Construction cycle options + ordered candidates + current native prices
pre-Gather demand
  -> research offer observation -> one lazy demand sample for the current demand epoch
  -> shared resource reservations/demand used by Storage, Build, Factory, Jobs/Craftsmen and later consumers
Storage -> [invalidate if capacity/quantity changed] -> Build -> [invalidate if construction action attempted]
Factory -> [invalidate if changed] -> Jobs/Craftsmen -> Fleet/Mech/... -> Power
Research mutation -> invalidate offers/demand -> new current Building observation -> Build
```

## Attribution method and limits

The P9 probe records a price event once at `probePrice`, with worktick, phase, action ID, `readCost`/`readCosts`, outcome, epoch, caller stack, and elapsed callback time. That event corresponds to one `buildQueue.setData` call. The normalizer adds the initiating feature, distinct downstream consumer labels, and the fact that the temporary queue probe does not mutate authoritative game state. It does not count both the probe parent and its `setData` child as independent price operations.

P6 records full Building observations, availability evaluations, native method counts, phases, and action attempts. P7 provides exact measured-window counts for selected readers and maps direct reader samples. P2/P7 sample profiles are used as exclusive leaf/callsite weights; inclusive parent stacks (`runPhase`, `runCycle`, `readCost`, `setData`, `adjustCosts`) overlap and are never added together. If initiating-feature or mutation ownership is not observable at a hook boundary, the report retains `unknown` rather than assigning it by proximity.

The observations and probes have different denominators: native price counts are exact, P6 Building observations include only complete current catalog reads, P7 counts are selected function entries, and profile percentages are weighted JavaScript samples. Their values must not be added into one workload total.

## Mutation, freshness, and bounded scheduling

The runtime's `demandThisCycle` is constructed lazily and reused only while its demand epoch remains current. It resets at each worktick. The unconditional invalidation at cycle start is a lifecycle boundary; it does not by itself show that relevant game state changed. Settings refresh invalidates demand separately from price authority. Root replacement invalidates demand, offers and control discovery state. The price-sensitive phase wrapper snapshots selected upstream price authorities before and after certain phases, but external or unwrapped mutations remain a limit; an unchanged `actionCostEpoch` does not prove all native prices fresh.

Explicit sample boundaries include confirmed Storage quantity/capacity changes, Trigger actions or uncertain partial failure, Research progression changes or uncertain reads, Construction action attempts, Factory changes, outer Fleet shipyard changes, and Mech pending work. Native controls also carry a generation: a tab draw can replace handles even if game authority did not change. P6's Construction-local memo was valid only within one synchronous `beginCycle()` after control discovery; it was not valid across the subsequent executor or phases.

An incremental planner may cross workticks only if it owns a frozen, immutable input and cannot issue a command while incomplete. Its continuation must validate an explicit token for every dependency it uses; the current demand epoch is scoped to one worktick and cannot establish cross-tick validity. At minimum, track root generation, settings revision/fingerprint, control generation, relevant progression/catalog epochs, and any relevant price/sample authority. A relevant version change discards the continuation and restarts from a fresh sample. A failed or partial action invalidates plans conservatively. Price plans need a narrower dependency declaration than one broad action-cost epoch; until that dependency is proven, any price-affecting mutation cancels them. A settings edit must cancel planning even when prices did not change. A native draw must refresh handles and either validate the captured catalog or restart. No asynchronous Vue state transfer or worker thread is needed or proposed.

Keep the immediate Build/Storage/Research controls on their current synchronous path. The next experiment should be a standalone deterministic planner harness over an immutable captured allocation snapshot: split pure search into a fixed work budget per tick, retain a continuation only while its explicit dependency token matches, and produce no commands until complete. Exercise root replacement, settings edits, control redraw, relevant resource/offer changes, price-authority changes, and failed actions as invalidation cases. Measure per-slice time and restart frequency in the exact runner; compare plans/commands and save exports, not renderer CPU A/B. If snapshots become obsolete faster than planning can complete, bounded scheduling is not viable; restart the allocation plan with conservative candidate and evaluation limits instead.
