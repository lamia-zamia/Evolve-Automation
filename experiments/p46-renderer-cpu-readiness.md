# P46 — Renderer CPU variance attribution and optimization readiness

## Decision: C — no justified optimization

The 2% renderer CPU gate remains unresolved. The current production profile has expensive paths, but source and call-order review found no redundant owner observation with a complete freshness contract. No production change, allocator, economic-policy change, or Research selector was added.

The bounded P46 measurements, raw process rows, workload calibration, paired effects, host-load samples, callback profile, and phase attribution are in [p46-renderer-cpu-readiness-evidence.json](p46-renderer-cpu-readiness-evidence.json). The reproducible harness is [p46-renderer-cpu-readiness.mjs](p46-renderer-cpu-readiness.mjs); the process-attribution checks are in `tests/experiments/p46-renderer-cpu-readiness-test.mjs`.

The treatment loop mutates only local numeric variables; it does not read or write game state, DOM, RNG, controls, or automation globals. Final exports, RNG counts/state, native control counts, and assignments are checked for parity.

### Measurement vocabulary

- **Renderer process CPU** is cumulative Chromium process CPU from browser-target `SystemInfo.getProcessInfo`, selected by stable renderer PID. It includes upstream game, automation, Vue, DOM, and other work in that renderer. It is the CPU measure used for the 2% decision.
- **CDP `TaskDuration`** is a page-target task-time counter. It is a calibrated cross-check, not process CPU and not automation-only time.
- **CDP `ScriptDuration`** does not cover the runner's controlled `Runtime.evaluate`/`advance()` workload reliably. Stage 4F.3's calibration showed zero `ScriptDuration` for controlled integer work that appeared in both renderer CPU and `TaskDuration`; this remains a required constraint.
- **Native monotonic callback duration** uses the page's original `performance.now()` around main-loop listener dispatch. It is synchronous elapsed occupancy, includes game plus automation, and is not CPU.
- **Main-thread latency** and Node **wall duration** include their own scheduling boundaries. Node wall time also includes CDP orchestration; neither is a CPU substitute.
- **Whole-game versus automation-only CPU:** this runner has no real boundary that separates the two. P22's exclusive owner timers can attribute synchronous elapsed segments, but they do not partition process CPU. Native calls made by automation can synchronously execute game and Vue work.

## 2. Reconstructed benchmark boundary

The exact runner lives in the nested `tools` checkout. Each `createChromiumRunner()` starts one headless Chromium browser and a local page server. Each `openSession()` creates a new isolated browser context and page, injects the bridge before page scripts, loads the upstream `index.html` at the pinned source commit, and runs the production bundle in the game page's main execution world. P22 created one runner per report and recreated contexts/pages for repeats; it had no virtual-period warmup. P46 records browser PID, page target, process rows, and renderer PID for every measured window, then repeats the control set in a separately launched Chromium process. The browser process is reused for multiple windows in each block, but `openSession()` creates a new page renderer for each window; P46 does not claim repeated measurements on one renderer PID.

The runner waits for page readiness and native game initialization before starting counters. Those load, import, and setup costs are excluded. The bridge owns virtual time: each requested period advances the game timer, dispatches the real game/automation listeners on the renderer main thread, and yields through browser task boundaries. P46 uses the ordinary bundle with `perf`, callback profiling, and native tracing disabled for CPU controls. It changes no browser launch flags and sets no CPU affinity. The 160-period CPU window implies 20 scheduled work ticks at `tickRate=8`; this is derived from bridge cadence and not instrumented in each CPU arm. The separate diagnostic pass observed 100 work ticks over 800 periods.

P22 read process CPU and page metrics concurrently before and after `advance()`. P46 serializes sampling. A clean window reads metrics, then process CPU, advances, reads process CPU, then page metrics. For a positive-control pair it also samples metrics and the same renderer process immediately around the extra `Runtime.evaluate`; the control executes an empty evaluation at the same point. The first and final renderer ID sets must match, the active renderer must account for at least 98% of renderer CPU in the window, and every intermediate sample must preserve the same renderer ID set. Renderer creation/termination or ambiguous activity invalidates attribution rather than being silently summed. Process identity passed for every retained counter read, including all three direct-workload calibration reads.

The final process CPU sample follows the last requested period (or the synchronous test loop). State snapshots, export, decoded state, diagnostics, hashing, and report assembly happen afterward. There are no per-period snapshots. P46 stores all raw process rows and sampling timestamps. `TaskDuration`/`ScriptDuration` use the game page CDP target; process CPU uses the browser target. The runner does not attach page metrics to an Evolve worker. The pinned page runs game logic and automation in one main execution context; the runner's timer Worker only paces messages.

`os.cpus()` host-wide busy percentage and Node process CPU are captured as covariates around each window. Chromium process rows expose browser/renderer/utility CPU; the harness does not enumerate or attribute every unrelated host process. Host contention and frequency scaling can therefore affect renderer results even when unrelated process CPU is not present in the renderer counter.

## 3–5. Control results, positive-control sensitivity, and alternatives

P46's same-save, same-seed, same-epoch, same-bundle no-op controls show large short-window spread even though their export, RNG, and native-control results match. The six controls in one browser process have renderer CPU mean 6.375 s and range 6.074–6.874 s (12.54% of mean); `TaskDuration` range is 14.71% of mean. The three controls in the second browser process have CPU mean 6.414 s and range 6.311–6.547 s (3.68%); `TaskDuration` range is 5.04%. These are p160 windows and are not pooled with P22's p800 or P13O's p1000 controls. The pre-control mean was 6.592 s and the post-control mean 6.159 s, a 6.57% shift over the run sequence. Export hashes alone therefore do not establish CPU parity.

The direct positive control is a deterministic local integer loop in the already-loaded page. Its iteration dose was calibrated from renderer process CPU, using three 30-million-iteration reads: 55.405, 44.655, and 43.920 ms. The median raw calibration rate was 1.47625 ns/iteration. The first call was slower than the next two, consistent with possible first-call/JIT effects, but not proof of JIT as the cause. `TaskDuration` moved by 54.299, 43.057, and 43.314 ms; `ScriptDuration` was zero in all three reads, preserving the Stage 4F.3 finding. The later positive-control calls used fresh pages, so their measured direct CPU deltas also include any per-call setup that remains inside `Runtime.evaluate`.

Six pairs ran in counterbalanced order (two per dose, one control→treatment and one treatment→control). Each arm independently loaded the identical fixture and advanced 160 periods, then performed a no-op or the local loop. The paired whole-window CPU and `TaskDuration` include the p160 game-plus-automation advancement and the extra no-op or loop evaluation. Separate immediate before/after reads around `Runtime.evaluate` measure direct loop CPU. The extra work did not change the game: all pair exports, RNG call counts/state, native control counts, and control usage match. The no-op p160 windows all had export SHA-256 `8040e2cb679715b9e972e77b760c38462572482292226c4a6922fdc1bf1d0578`, 422 RNG calls, final RNG state `1276349696`, and 24,023 native control calls. The 800-period diagnostic ended with 2,194 RNG calls, state `2697293500`, 117,166 control calls, and export SHA-256 `a99e0f35aa7cb5b4c9f3f3a7ed93963f5b3382cf4194737218474e927c48168a`. Its separate native-trace invocation count was zero; that is not the same counter as `controlCallCount`.

The 2% loop itself was recovered at 1.992% of baseline renderer CPU (95% CI 1.664–2.320%), and the paired total-window CPU point effect recovered 103.8% of that direct workload. However, the paired total CPU 95% interval was −0.171 to +0.444 s (−2.60% to +6.74% of baseline), so it includes zero. Both observed 2% pair effects were positive, but this is not sufficient for the gate. The 5% pair effects changed sign with order. The 10% loop was measured at 9.671% of baseline and its paired total CPU effect was 0.696 s (95% CI 0.444–0.948 s), recovering 109.1% of the direct workload. Thus the protocol detects the 10% control, while its predeclared two-pair budget cannot establish a 2% effect.

Intervals use paired two-sided t intervals. With two pairs per dose, `df=1`; these deliberately expose the small sample's uncertainty. The expected 2% effect is not established by this run. `ScriptDuration` remained zero for each controlled loop read, while direct renderer CPU and `TaskDuration` tracked the loop. All counter reads passed renderer PID attribution and per-read identity. The two browser process IDs differed as intended; renderer IDs changed between page sessions within each browser process.

Warm controls were lower (5.422 s CPU mean and 4.794 s `TaskDuration` mean, n=2) than cold controls, but they advanced the game by 160 periods before timing, so game state and production work also changed. This is not an isolated JIT-warmup comparison. The diagnostic callback latency was 168.74 ms mean / 227.3 ms p95 in the first 50 work ticks, with a 556.1 ms maximum, and 149.05 ms mean / 182.4 ms p95 in the second 50. These are instrumented game-plus-automation callback elapsed times, not CPU. The V8 compile-duration metric delta was zero. `PerformanceObserver` reported GC entries unsupported, so GC was not observable in this run.

Same-browser cold controls had renderer CPU/order correlation −0.816 and CPU/host-busy correlation +0.792 (n=6); the fresh-browser controls were −0.680 and +0.407 (n=3). The reused-browser controls were higher before the paired block than after it, while host busy percentage also shifted from about 31–32% to 18–25%. Run order, host load, and the measurement phase are confounded; these small samples do not identify a cause. Node CPU usage was negligible in these windows. The harness observes system-wide busy percentages but does not enumerate unrelated processes.

The P46 windows use the direct renderer process counter with strict per-read PID checks, a no-op side of each treatment pair, and a fresh-browser control. They do not reuse one renderer across repeats because the exact runner recreates the page. P2/P8/P13O/P22 show that simply extending the total window has not produced a reliable 2% comparison in their distinct fixtures and timing boundaries; those results remain separate. A same-renderer repeated-page comparison and a true game-versus-automation CPU split are not available in this runner. The P46 owner profile below uses native elapsed timing only and cannot substitute for CPU.

## Decision and verification

The final decision is **C — no justified optimization**. Renderer CPU tracks the deterministic workload, and the protocol clearly detects the 10% control, but the 2% paired interval includes zero and the 5% results are order-sensitive. Same-state no-op controls vary by 12.54% in the reused-browser block for these short windows. The ≤2% gate remains unresolved; do not use it to admit future autonomous allocation. The current hotspots are expensive but necessary owner observations, with no verified removable duplicate.
