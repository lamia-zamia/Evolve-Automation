## Decision

No production change is justified by this audit. The refreshed profile keeps Vue's `get` handler high in the ranking, but the largest individual direct automation reader accounts for about 0.4–0.7% of weighted JavaScript samples, and the safe fraction of that reader is smaller. Call-count instrumentation confirms frequent repeated reader invocations; it does not establish that their answers can be reused safely. The highest-volume availability path invokes live native `condition()` callbacks, and other large paths cross mutable feature phases or native price probes.

The no-change decision is specific to this baseline and these fixtures. It does not claim that the readers are free or that a later profile cannot identify a narrower same-operation duplicate.

## Setup and method

The `deadspace` worktree was clean at the requested starting commit. This branch was created directly from that commit; no P4 change or production source was carried into it. The P2 Chromium profiler was adapted to accept a bundle override. It ran the pinned late and mid saves with seed 42, 600 warm-up periods, and 1,000 profiled periods, using two fresh sessions per fixture and a 1,000 μs CDP sampling interval. The runner used the pinned DeadSpace snapshot and its unmodified game page.

Source attribution uses an esbuild source map generated from the same `src/main.ts` and production build options. The generated bundle body was compared byte-for-byte with the production bundle before mapping. The profile itself used the production bundle, with no profiler or source-map instrumentation in its runtime code.

Thus explicit automation-owned stacks account for about 49% of getter samples late and 30–31% mid when direct property reads and native callbacks explicitly invoked by automation are combined. The worker wrapper's presence alone does not make the nested `fastLoop` getter work automation-owned. The earlier P2 attribution is not reused as a current value.

The automation-owned getter samples split across many call paths. The heaviest _single direct reader_ is building action availability; the whole Vue `get` bucket is not a single optimization target. Inclusive parent stacks such as `runPhase`, `runCycle`, and `worker-capture.ts:wrapper` overlap their children and are not added to candidate weights.

`readProperty` itself was called 5,911,679 times late and 2,827,948 times mid during the measured windows. ## Mutation-boundary and native-authority evidence

- `readCapturedActionAvailability` calls the action's `condition` synchronously. The pinned upstream `src/space.js:checkRequirements` also invokes action conditions as part of native eligibility. A condition can inspect live state; hoisting its result or state facts across actions would change the observation boundary. Native condition execution remains authority.
- `readCapturedActionControlAvailabilityForTab` performs additional tab, region, and renderer gates before invoking the shared action-availability reader. Duplicate `settings` / `race` / `tech` record traversals are evident in the same stack, but its operation can call conditions and feature phases can issue commands between later reads. The safe sub-boundary is smaller than the 57,000 / 22,608 outer call count.
- `readCost` deliberately mutates the queue temporarily and asks the game's `setData` for each answer. Its `finally` rollback protects player entries after failure. Reusing one action's result for another action or a later phase lacks a freshness proof.
- Construction and demand run as ordered application phases. A reader that appears more than once in their inclusive stacks can be a required fresh sample after an earlier effect. Stack overlap alone does not prove redundancy.
- The temporary call-count bundle reset its counters after the 600-period warm-up and counted 1,000 measured periods. It exported byte-identical saves and identical control-usage maps to the production-bundle profile for both fixtures, with no captured page errors or dialogs. It was used for deterministic operation counts only, not timing.

## Reliability, artifacts, and recommendation

The P4.2 reliability report (`experiments/p4-benchmark-reliability.md`) found same-bundle false A/A effects up to tens of percent and a 5.98% standard deviation even in its quieter fresh-mid controls. This audit did not run a production A/B or infer savings from the profiled renderer totals. The P7 repeat spread is also large enough late to keep those totals descriptive only.

Raw profiles, generated source map, and exact call-count JSON are ignored scratch artifacts under `test-artifacts/perf-profile/` and are reproducible from the P7 helpers. A first call-counter attempt inserted code inside a function's default-options object and failed syntax checking; that run's empty counters and mismatched hashes were discarded. The corrected balanced-parameter scan produced the parity-matched counts above.

No production files or tests were changed. Tooling changes and this report are committed separately. Stop here for independent review; revisit implementation only if review identifies a bounded synchronous reader with a larger proven removable-work budget.
