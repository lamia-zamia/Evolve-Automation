## Decision

**D. No saved scenario currently supports a representative executable strategy comparison.** The Stage 3T Steel Containers case remains the closest concrete frontier, but its ordinary Build commitment already covers the resource gap. A later MAD save has no shortage in the resources the Smelter can redirect, and the fresh save has no characterized goal/action pair. No experiment was run that could only reproduce the baseline decision. Production strategy integration remains out of scope.

## Experimental defect corrections

`experiments/stage3s-strategy-pilot.mjs` now obtains Iron and Steel stock from the supplied current `root.resource.<id>.amount`, validates it as finite and non-negative, and refuses a candidate if the current root generation differs from the native Research catalog generation. It no longer reads `SmelterInput.ironCount` or `steelCount` as inventory; those fields are smelter assignments.

The test-surface hook now receives the current root and root generation with the selector result. `applyCapturedSmelterTestCandidate()` accepts only an explicit Iron or Steel result with a native action identity, a matching stock identity and amount, an unchanged root object, and an unchanged root generation. It turns on only the corresponding existing demand boolean. Invalid identity, unsupported resource, absent or negative stock, mismatched stock, and stale root evidence preserve the original input.

Focused regressions cover live stock versus allocation counts, invalid and unavailable stock, candidate identity, and Iron/Steel demand-field isolation. The production Smelter planner and settings are unchanged; the experimental hook remains compile-time test-surface-only.

## Stage 3T exact-demand boundary

The Stage 3T settings set `autoARPA: false` and enable nine persisted/effective project switches: Launch Facility, LHC, Stock Exchange, Monument, Railway, Nexus, Roid Ejector, Syphon, and TP Depot. The current save is at High Tech 2 and has an empty `arpa` state. The native `src/arpa.js::physics()` only draws the native project catalog at `high_tech >= 6`; `progression.readEstablishedProjects()` therefore has no captured catalog. The refusal is expected for this save. It is a missing current catalog, not evidence that an unknown project price is zero.

Each Stage 3T `sampleExact()` passed its earlier exact prerequisites and then returned `project-storage-catalog`. The demand adapter sets that refusal when enabled project-storage settings exist but the native project reader returns `undefined`. Effective `autoARPA: false` does not erase the enabled project switches. A future project’s native resource costs are not inferred from its absence here.

The boundary has two distinct outputs. Captured spending requests—including queue reservations, offered Research costs, construction-saving, triggers, and other prepared demand inputs—are combined into `requestedQuantity` before the project catalog is read. Project costs are consumed by `planStorageRequirements()` as `projectStorageTargets`, affecting `storageRequired`; they are not added to `requestedQuantity`. In this run all earlier exact gates were complete, so a resource-scoped _spending request_ observation could be derived from the existing request calculation independently of this project-storage refusal. That would not establish storage headroom or authorize a strategy that can displace capacity needed by an enabled project. No global exact-demand behavior was changed and no new capture framework was added.

## Minimum separation of strategy and safety

Future experiments should keep these facts separate:

1. **Proven prerequisite:** current native goal requirements establish that an action advances a required grant/level.
2. **Valid candidate:** a current native action is offered, eligible, priceable, and bound to the current root/progression/offer generations. It is an option, not a reservation.
3. **Selected strategy:** among candidates that safety permits, an experiment may choose one using estimated opportunity cost and downstream milestone value. Mathematical necessity is not required.
4. **Authorized native execution:** the existing explicit owner permission is enabled; the native action remains current and affordable; current commitments are complete for the affected resources; existing commitments are preserved; and all evidence is revalidated immediately before invoking the native control.

Strategy cannot make an unavailable action eligible, alter stock or technology, or reserve spending by selection alone. No production path was connected to this experimental selector.

## Comparison protocol and measured evidence

The closest future candidate is a genuinely underproduced resource on a selected native progression route, with a fresh native action price, two feasible Smelter plans, complete current spending-request evidence, and separate complete storage/capacity evidence. Freeze one save, pinned snapshot, settings, seed, horizon, and native permission. Compare the baseline planner with a test-only strategy that selects a different permitted Smelter alternative, revalidates immediately before native execution, and never edits game values directly.

Measure the first downstream native progression milestone and later technology grants, along with resource stocks/rates, allocations, fuel/upkeep, capacity use, competing construction demand, idle periods, control calls, and execution outcomes. Time-to-goal estimates from instantaneous rates are uncertain because rates change with fuel, buildings, demand, storage, and allocation; report measured milestone periods as primary and projections only with a stated range. Do not execute an A/B when the candidate leaves the native planner decision unchanged.

Existing Stage 3T B/D evidence is the only applicable comparison here: both conditions reached Steel Containers at p1072 and Industrialization at p3560, and both ended at High Tech 3 with identical tracked resources and allocations. It demonstrates equivalence for this fixture, not a strategy gain. No new strategy replay was justified.
