# P24 — Pure Jobs planner cost isolation

## Decision B

Stop pursuing Jobs threading. The pure planner takes a median **0.10 ms** per real full Jobs invocation (p95 0.20 ms, p99 0.30 ms, maximum 1.10 ms). It accounts for **0.66%** of the measured capture + plan + execute elapsed time. A 14.7 KB captured input takes a median 0.10 ms to structured-clone in the page, before worker startup, message handling, result validation, or cleanup. The available result deadline is inside the same synchronous owner callback, so an asynchronous Worker result cannot replace the decision without changing execution order.

No Worker was started or integrated. The conditional Worker verification was not reached because the workload failed both the cost and scheduling gates. P22's renderer CPU control spread remains 3.23%; no renderer CPU claim or factorial was made.

The planner input and output contain structured-clone-compatible scalar values and arrays. `planJobs()` uses local maps and arrays internally; it has no DOM/native object or closure dependency. A proposed result would still need current root identity, prepared generation, settings and Jobs/foundry state, multiplier-latch state, required live control methods, and the existing postcondition before it could carry authority. The worker could not eliminate native capture, demand/cost reads, control checks, or execution.

## Measurement

The existing ordinary `jobs.full.plan` diagnostic encloses `reader.readCycle()` and `planJobs()` together; the full prepared path already separates `jobs.full.read` and `jobs.full.plan`. Those diagnostics report aggregate phase times and counts, not per-invocation distributions. The experiment uses P22's `late-many-owners` save/settings pair, seed 42, epoch `2026-09-21T00:00:00.000Z`, and 800 periods / 100 work ticks. The standard production bundle was not modified. The P24 script builds a temporary test-surface control bundle and a second test-surface bundle with local esbuild transforms that bracket the existing capture, `planJobs()`, and execution calls. The ordinary execution path still makes its original single planning call; the full prepared path still makes one. Timing callbacks run only after each captured input or decision exists. No native reads or planner calls were added to a cycle.

The uninstrumented test-surface control and timing build had identical work-tick and native invocation sequences, RNG count, state hash, and exported-save hash. Both had 100 work ticks and 2,194 RNG calls; each recorded 243,390 native invocation events. ## Scheduling gate

Full Jobs capture, planning and prepared execution happen synchronously inside the current `autoJobs with autoCraftsmen` owner callback. That decision must be consumed before the callback returns and before later owners run. Deferring it would move execution relative to those owners. Accepting it next cycle would require revalidating fresh resources, prices, demand, settings, controls, generations and every other decision input; the current path deliberately rejects stale state. The measurements establish no safe asynchronous window.

Only the pure planning segment is a theoretical main-thread removal candidate: approximately **0.66%** of the measured Jobs segments, before clone/transfer, startup, message and result-validation costs. Capture dominates and is native state/cost work that a Worker cannot remove. With no schedulable window and clone cost comparable to planner time, further Jobs threading work is not justified.

## Reproduction and limits

Run `node experiments/p24-pure-planner-cost-isolation.mjs` from the repository root. It uses the exact Chromium runner and does not change the runner or its controlled game-timer Worker. It records a P22-matched control and instrumentation comparison but does not measure Worker startup or round-trip time because the worker-worthiness gate failed. A real-Worker compatibility test is therefore unnecessary for decision B.
